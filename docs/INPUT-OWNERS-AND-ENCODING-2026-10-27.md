# Владельцы запрета зарядки и ошибка кодирования входного тока

27.10.2026. Продолжение BOOT-STORM-REVIEW. Только разбор архивных бинарников
и исходников в Ghidra. **Нет новой сборки, установки, тестов, эмуляции,
перезагрузки или обращения к аппаратным регистрам.**

## Что установлено

Два компонента независимо отправляют одну команду управления приостановкой
питания: qcpmictcc1680 и qcbattmngr10730. Battery manager сохраняет последние
запрошенные значения и может пропустить повтор команды, не перечитывая
реальное состояние. Другой компонент меняет питание вне этой сохранённой
копии. Это конкретная несогласованность владения состоянием, способная
оставить зарядку выключенной при определённом порядке событий.

Отдельно в исходном PMIC1840 найдено неверное кодирование запроса входного
тока: умножение на1000 с последующим усечением до байта вместо пересчёта
по шагу регистра. Нижний qcpmic передаёт этот байт на шину без исправления.
Прохождение прежних сбоев по этим путям и фактический ток сейчас
не измерялись. Эти находки не объявляются доказательством устранения
всех неисправностей USB/SSD или отсутствия будущих BSOD.

## OWNER-01. Второй писатель найден

В прошлом отчёте отсутствие обратной команды было ограничено путём Type-C.
Теперь найден её другой отправитель — battery manager RVA17EE8.
Следовательно, утверждение «Windows нигде не может снять suspend» было бы
неверным. Правильный вопрос: выполняется ли повтор после внешнего изменения.

17EE8 вычисляет желаемые USB/DC suspend-флаги из внутреннего состояния
контекста+A88. Например, в нескольких ветвях USB suspend равен0; некоторые
другие состояния требуют1. Это реальные разные запросы, а не константа1.
Значения внутренних состояний не переименованы по догадке в «зарядка/сон».

Далее проверка машинных инструкций:

```text
1806C: прочитать cacheValid из глобального RVA2911B
18080: сравнить desiredUSB с savedUSB, RVA29121
1808C: сравнить desiredDC  с savedDC,  RVA2911A
18094: если valid && оба совпадают, перейти к18190
       // пропустить отправку801B0FE4
180A8/180AC: иначе записать desiredUSB/DC в поля+4/+5 буфера
18114/18118: сформировать IOCTL801B0FE4
18124: отправить запрос
18130..18140: проверить NTSTATUS, vendor-status и длину ответа4
18188/1818C: после успеха сохранить USB/DC
181F8: выставить cacheValid=1 после завершения следующих операций
```

Переход18190 также сравнивает кэш другой операции управления зарядом, но
**не читает1340/1440** для сверки suspend. Прямые xref глобальных2911B,
29121,2911A в этом модуле найдены только в17EE8. Указательная запись или
внешнее изменение глобальной памяти этим поиском полностью не исключены.

Type-C1680 отдельно в9AA0 после серии SwtchInt отправляет801B0FE4 с
USB=1,DC=1. Это тот же тип команды, которую battery manager может отправить
с нулём для USB. В PMIC1840 команда приходит в2628 и далее в нижний транспорт.

## OWNER-02. Возможная последовательность застревания

Это **статический вывод из ветвлений**, а не запущенный тест:

1. Battery manager успешно запросил допустимый набор USB/DC и запомнил его;
   USB suspend в этом наборе равен0, cacheValid=1.
2. Type-C recovery независимо запросил USB=1,DC=1.
3. Battery manager снова выполняет17EE8 с прежним желаемым набором.
4. Проверка кэша видит «значения не менялись» и не отправляет восстановление.

Для этого сценария не нужен одновременный доступ двух CPU: достаточно
последовательных записей разных владельцев. Обычный mutex вокруг отдельных
запросов сам по себе сохранённую копию не исправляет.

Не доказано, что предыдущий сбой прошёл именно так. В реальности другое
событие может изменить желаемые флаги, заставить повторить команду или
перезагрузить компонент. Кэш также не доказывает, что suspend будет висеть
вечность. Но ветвь пропуска позволяет не восстановить его при неизменной
политике. Периодический вызов17EE8 сам по себе проблему не исключает.

## TRANSPORT-01. До какого уровня прослежены записи

```text
qcpmictcc9AA0 или qcbattmngr17EE8
  -> IOCTL801B0FE4
  -> qcpmicext2800 ->2628
  ->5C78: запись1340, и5E10: RMW1440.bit0
  ->4AC8: WDF-запрос802B0FA0
  -> qcpmic60D0
  ->F5E0 -> интерфейс шины
```

5C78 передаёт структуру: SID=2, адрес регистра, значение байта. Первая2 —
идентификатор PMIC/slave, а не код операции. В нижнем60D0 ветвь802B0FA0
берёт младший байт поля значения, передаёт буфер длиной1 вF5E0. F5E0
формирует адрес `reg | (SID << 16)` и вызывает транспорт с тем же буфером.
Дополнительного перевода тока или напряжения в этом пути нет.

Это подтверждает семантику **запрашиваемой** записи. Успех исполнения
конкретного запроса на планшете не наблюдался. Старые снимки R5 по-прежнему
не содержат1340. Нельзя задним числом объявить измеренный suspend=1.

Декомпилятор показывает4AC8 как void; это метаданные Ghidra. В машинном
коде результат WDF-вызова вW0 сохраняется до RET и используется вызывающим
кодом. Не делать из ошибочного прототипа вывод, что функция не возвращает
статус.

## ENCODING-01. Запрос тока обрезается до байта

Battery manager213A8 формирует вход801B0FA0. Поле+0xC берётся из четвёртого
аргумента функции с ограничением4800. В том же коде есть сравнение этого
аргумента с500/900, а соседнее поле напряжения ограничено диапазоном
3487..4920 (0x0D9F..0x1338). Это согласуется с ABI мА/мВ, а не с уже
закодированным байтом; для входного тока особенно показательны500/900.
В обычном пути17428 функция213A8 вызывается при изменении вычисленных
параметров; сохраняется также кэш этих параметров.

В исходном PMIC1840 диспетчер801B0FA0 вызывает1C28. Для поля+0xC:

```text
1CF4: LDR W8,[input,#0xC]
1CF8: MOV W9,#0xE8
1D00: MOV W2,#0x1370
1D08: MUL W8,W8,W9
1D0C: UXTB W3,W8
1D10: BL 5C78
```

То есть в USBIN_CURRENT_LIMIT_CFG запрашивается
`raw = (input * 232) & 255`, эквивалентно младшему байту `input * 1000`.
Ни деления на шаг, ни проверки допустимого кода в этой ветви нет.

В Android таблица именно PM8150B задаёт для USB ICL минимум0, максимум
5000000мкА, шаг50000мкА. smblib_set_charge_param сначала ограничивает значение,
затем вычисляет `(value_u - min_u) / step_u`. Функция разобрана в ELF
по адресуFFFFFF8008C98638: проверка границ и деление перед записью
подтверждены машинным кодом.
[Таблица параметров nabu](https://github.com/MiCode/Xiaomi_Kernel_OpenSource/blob/71b6effd2dfa8f703dd1ea17acd1323b2fd3cf6c/drivers/power/supply/qcom/qpnp-smb5-nabu.c#L124),
[преобразователь](https://github.com/MiCode/Xiaomi_Kernel_OpenSource/blob/71b6effd2dfa8f703dd1ea17acd1323b2fd3cf6c/drivers/power/supply/qcom/smb5-lib-nabu.c#L724).

Простая арифметическая иллюстрация формул, без запуска драйвера/эмулятора:

| Запрос мА | Код при шаге50мА | Код Windows1C28 |
|---|---|---|
|1500|30 /0x1E|96 /0x60|
|3000|60 /0x3C|192 /0xC0|

Код96 по таблице соответствует настроенному пределу4800мА; это **не
измеренный потребляемый ток**. Реальный ток зависит от источника,
согласования, защит и нагрузки. Код192 выходит за описанный диапазон
0..100; поведение железа на нём не установлено. Записывать эти значения
ради проверки запрещено текущими ограничениями.

В1C28 такая же операция умножения/усечения используется для1061,1070,118C.
Повторная сверка извлекла отдельную таблицу именно PM8150B:

| Регистр | Назначение | Единицы Android | Минимум | Максимум | Шаг |
|---|---|---|---|---|---|
|1061|FCC, ток заряда батареи|мкА|0|8000000|50000|
|1070|Float voltage|мкВ|3600000|4790000|10000|
|1370|USB input current limit|мкА|0|5000000|50000|
|118C|DC input current limit, DCDC_CFG_REF_MAX_PSNS|мкА|0|1200000|40000|
|1152|OTG current limit, отдельный регистр|мкА|500000|2000000|500000|

**118C — не OTG current.** Последний параметр1C28 нельзя автоматически
трактовать как питание USB-хаба: OTG-лимит находится по1152. Для DC ICL
шаг PM8150B40мА, а не50мА из другой таблицы PMI632. Это пример того,
почему один общий коэффициент для всех полей неверен.

Для1070 требуется также вычитание смещения3600000мкВ; одно исправление
множителя не решит кодирование напряжения. Максимумы таблицы — пределы
регистра, а не разрешение подавать их в реальном подключении. В DTS nabu
есть отдельные board-пределы USB ICL3000000мкА, FCC5900000мкА и FV4470000мкВ,
которые дополнительно ограничиваются контрактом, температурой и батареей.
Нельзя присвоить эти board-максимумы текущему зарядному блоку без согласования.
Артефакт REGISTER-ENCODING-SPEC.json извлекается из точного исходника.

Исторический1370=0x60 совпадает с одним арифметическим результатом,
но исходный запрос1500мА в том захвате не зафиксирован. Совпадение не
доказывает происхождение исторического значения и не измеряет зарядный ток.

## Что именно делает Android с несколькими ограничениями

Дополнительно найден и сохранён точный исходник battery.c того же commit.
Он создаёт USB_ICL как VOTE_MIN и назначает usb_icl_vote_callback.
Этот callback разобран в архивном ELF по адресуFFFFFF8008C8DC60: установка
эффективного ICL идёт через свойство основного charger, с дополнительной
логикой parallel/AICL. Он относится к общему battery/parallel-слою, а не
к функции с таким же назначением внутри smb5-lib.
[battery.c, обработчик](https://github.com/MiCode/Xiaomi_Kernel_OpenSource/blob/71b6effd2dfa8f703dd1ea17acd1323b2fd3cf6c/drivers/power/supply/qcom/battery.c#L1281),
[создание USB_ICL](https://github.com/MiCode/Xiaomi_Kernel_OpenSource/blob/71b6effd2dfa8f703dd1ea17acd1323b2fd3cf6c/drivers/power/supply/qcom/battery.c#L2031).

Полезный принцип для Windows — вычислять эффективное ограничение из
действующих причин и согласованного контракта. Снятие временной причины
BOOST_BACK не должно снимать температурный запрет или превышать лимит
источника. «Всегда обнулять1340 при подключении» не является решением.

## Как меняется спецификация исправления

Нужен один владелец фактических записей suspend/ICL. Остальные участники
передают ему запросы с причиной и поколением подключения:

| Владелец намерения | Что хранится | Что нельзя делать |
|---|---|---|
|Battery policy|Базовое разрешение USB/DC и ограничения батареи|Считать последний запрос точной копией состояния после чужой записи|
|Type-C / PD|Допустимая роль, контракт и разрешённая мощность|Включать Source после перехода в Sink старым таймером|
|Recovery|Отдельная временная причина ограничения, условия выхода|Оставлять необозначенный запрет без пути восстановления|
|Thermal/fault|Самостоятельные запреты и пределы|Снимать их вместе с recovery|

Один mutex или принудительная повторная запись последнего значения не
заменяют эту модель. Для закрытых компонентов потребуется согласованный
интерфейс: старую801B0FE4 нельзя надёжно разделить по владельцам, угадывая
их по процессу/стеку вызова. Спецификация должна явно отличать базовую
политику батареи и временный запрос Type-C recovery. Это проект решения,
не уже реализованный новый драйвер.

Снимок состояния помечается поколением и достоверностью; успешное завершение
команды обновляет только подтверждённые поля. При ошибке записи состояние
становится неизвестным, а не «успехом по кэшу». После удаления временного
ограничения повторно применяется эффективное состояние остальных причин.
Пересчёт каждого регистра выполняется из документированных единиц и границ.

Windows требует достоверно сообщать изменения источника/батареи и сохранять
аппаратную остановку заряда при полном аккумуляторе и неисправностях.
Поэтому восстановление зарядки нельзя свести к изменению значка.
[Microsoft battery/charging](https://learn.microsoft.com/en-us/windows-hardware/design/component-guidelines/battery-and-charging).

## Следующие конкретные незакрытые места

1. Согласовать ABI единиц на обеих сторонах с извлечённой таблицей регистров;
   проверить путь альтернативного charger и выбор chip/board-профиля,
   не объявляя его тем же.
2. Условия входа/выхода recovery и доставки события battery manager;
   определить минимальный согласованный интерфейс владельцев.
3. Свести это с ранее найденными проблемами Source-таймера, Sink-команд,
   Fault, готовности и остановки потока. Отдельный патч одного байта их не закрывает.
4. Непрерывность питания хаба остаётся отдельным аппаратным условием.

Чек-лист дополнен сценариями межкомпонентного восстановления и корректного
пересчёта токов. Никакие пункты не отмечены пройденными новой сборкой.
Рядом сохранены отчёты Ghidra, исходник battery.c, функции и манифесты.
