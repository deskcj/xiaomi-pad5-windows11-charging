# r3: переход SINK → SOURCE не восстанавливается; r4 — диагностическая версия

**r3/1845 прошла первую загрузку и заряжала с хабом/SSD после входа.
Тест отключения и возврата только зарядки — FAIL. Установлена диагностическая
r4/1846 прошла первую загрузку и чтение всех 14 регистров. Первое подключение powered-хаба: зарядка FAIL, SOURCE-only/OTG включён. Подробности — evidence/pmic-r4-first-attach.json и PMIC-R5-DRP.md.**

## Что измерено на r3

Перед тестом Power API: AC online, Charging=1, Discharging=0, SOC 92 %.
Запрос роли PMIC 0x802a0fa4 успешно вернул SINK в 21:36:03 (+05:00).
Во время одного цикла зарядки нативный журнал зафиксировал:

| Время +05 | Наблюдение |
|---|---|
| 21:40:26.193 | AC offline / Charging=0 |
| 21:40:29.240 → 30.242 | SSD исчез и вернулся; хаб оставался доступен |
| 21:40:39.360 → 40.370 | SSD ещё раз исчез и вернулся; хаб оставался доступен |

Read-only опрос роли с 21:40:33 до 21:48:01: 223 отсчёта, каждый SOURCE,
статус запроса 0. Владелец подтвердил, что зарядка возвращена, SSD виден,
зарядки нет. Точные времена физических манипуляций не измерены.
Это подтверждает сохранение роли источника после возврата зарядки,
но не доказывает, какой программный путь удерживает роль.
Счётчик Rate API после отключения ещё сохранял прежнее положительное значение;
он не использован как подтверждение входной мощности.
Целостность копирования при переходе не испытывалась; непрерывность USB не достигнута.

## Зачем r4

Общий GET_STATUS PMIC сам пишет OTG_CONFIG. Существующий чистый getter роли
даёт только SINK/SOURCE/UNATTACHED. r4 сохраняет политику r3 и добавляет
ограниченный read-only канал для снимка состояния и конфигурации.
Никакого нового автоматического сброса или переключения ролей нет.

У исходного callback 0x8BE0: MOV W0,#0; RET. Новый вход сохраняет нулевой
результат обычных вызовов. Только специальный диагностический пакет читает
один разрешённый регистр через уже используемый PMIC reader.
Используется существующий dispatcher 0x8DD0 и IOCTL 0x802a0fb4,
вход 16 байт, выход 4 байта. Дополнительных указателей от user mode нет.
Разрешены только logical index 1, SID 2, TYPEC base 0x1500.

Протокол: четыре DWORD [1, 0x51, 0x4e420000 | register, 1].
Успех: 0x4e420000 | byte, ошибка: 0x4e430000 | error16.
Нулевой ответ исходной заглушки не принимается за значение регистра.
Разрешён ровно список: 110d, 1140, 1153, 1307, 1308, 130b, 1310,
1358, 1370, 1506, 1508, 1509, 150b, 1544. Записей в новой функции нет.
Открытие диагностического устройства требует существующих административных прав;
ACL устройства и службы не менялись.

## Проверки подписанного SYS

- 3907 сценариев сохранения поведения r3;
- 882 сценария диагностического callback, 19 проверок полного исходного dispatcher;
- 333 нативных контекста RtlVirtualUnwind, ноль ошибок;
- Ghidra: новый callback вызывает только PmicReadByte, роль r3 сохранена;
- 14 клиентских векторов пакета, отказ на неразрешённом регистре;
- восемь проверок выбора recovery snapshot и baseline guard.

MSVC выдал два code-сегмента и 14 пар .pdata/.xdata. Сборщик сначала отказал
неподдерживаемому layout; добавлены явные размещения и сортировка runtime records
с отказом при прямых ссылках на .pdata. Все compiler unwind-данные сохранены.
Регрессионная сборка r3 тем же сборщиком дала прежний SHA-256 побайтно.
Импорты, CFG load configuration и исходные relocation-данные сохранены;
новых RWX-секций нет. Проверки не гарантируют отсутствие BSOD.

## Установка и следующий шаг

r4 была установлена как oem139.inf / 1.0.1846.0; первый ручной Restart прошёл.
Перед активацией сохранены полный SYSTEM ДО Stage, BCD и пакет 1845.
Внешние копии сверены; SYSTEM прочитан Offreg и python-registry.
Предпросмотр отката удаляет только oem139 и возвращает oem138/1845.
Фактический offline Apply не испытывался.

После загрузки без хаба сохранён снимок DRP/Try.SNK, OTG выключен.
При первом подключении хаба с зарядкой/SSD входное питание не появилось:
SOURCE-only, OTG включён. Новый протокол прочитал все 14 регистров,
отдельный getter подтвердил SOURCE. До подключения зафиксирован переходный
1509=07 без CC attachment; он попадает в старый диапазон fix20 5..34.
Точный источник вызова роли журналом регистров не установлен.
Следующий эксперимент — [r5 без подмены DRP на SOURCE](PMIC-R5-DRP.md).
Type-C lockfix остаётся отдельным неустановленным кандидатом.
Быстрая зарядка и HDMI здесь не добавлялись.

Android nabu использует отдельные операции OTG и роли, а для attach проверяет
бит TYPEC_ATTACH_DETACH_STATE_BIT вместо диапазона полного байта:
[официальный исходник Xiaomi](https://github.com/MiCode/Xiaomi_Kernel_OpenSource/blob/71b6effd2dfa8f703dd1ea17acd1323b2fd3cf6c/drivers/power/supply/qcom/smb5-lib.c).
Это направление сравнения, а не объявление переноса Android уже выполненным.
