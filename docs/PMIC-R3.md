# PMIC r3 / 1845: исправление ошибки переноса роли 0

**r3 / oem138.inf / 1.0.1845.0 загрузилась и заряжала. Цикл отключения/возврата зарядки FAIL: роль осталась SOURCE. Далее установлена r4 для диагностики.**

## Ошибка в r1/r2

Повторная проверка оригинального fix20 обнаружила ошибку нашего переноса:
в оригинале 0x2654 — CBZ x1, 0x267C. Специальная ветка выбирается по роли 0,
а не по индексу 0. r1/r2 дополнительно проверяли index==0 и на реальном nabu
индексе 1 сразу переходили в legacy role write. В результате обходился путь,
который мог снять OTG latch через 0x1140. Это изменение поведения внесли мы.

Прежняя формулировка «не переносить эвристику на индекс 1» была основана на
неполном разборе входного условия. Она исправлена: оригинальный вход относится
ко всем запросам role==0; сама полнобайтовая эвристика 0x1509 остаётся недоказанной
USB-PD политикой. Не надо путать исправление входного условия с её верификацией.

В backend qcpmictcc nabu индекс 1 передаётся в 0x802a0fac; PMIC slot 1 выбирает
контекст D180: SID 2, TYPEC base 0x1500. r3 сохраняет индекс вызывающего кода,
читает SID выбранного готового слота и запускает прежнюю ветку для роли 0.
Проверки индекса [0,1], готовности выбранного слота и ошибок SPMI сохранены.
Оригинальный Chinese код терял volatile-регистры; его ABI-дефекты не возвращены.

## Проверки

- 12 исполнений машинного кода original fix20/r2/r3 до первого вызова PMIC:
  подтверждено, что r2 пропускает чтение 0x1509 на index=1/role=0, а original/r3
  заходят в эту ветку. Аппаратные функции не исполнялись.
- Подписанный r3 SYS: 3907 ARM64-сценариев, все 256 значений состояния для обоих
  индексов, отдельно фактическая комбинация nabu index 1 / SID 2, ошибки и ASLR.
- Native Windows ARM64 RtlVirtualUnwind: 172 контекста, ноль ошибок.
- Ghidra: финальная ветка/вход просмотрены; сохранены пять пар .pdata/.xdata,
  нет новых импортов и RWX-секций. Подпись/принадлежность каталогу проверены.
- Семь проверок выбора recovery snapshot и отказа на некорректном baseline.

## Новая read-only диагностика 1844

PMIC 0x802a0fa4 / callback 0x88F0 только читает 0x150b и возвращает роль.
На неработающей зарядке ответил status 0, role 3 (UNATTACHED), хотя хаб/SSD
были доступны. Это ответ установленного драйвера, не измерение напряжения.
SID/порт проверены статически. Общий GET_STATUS 0x802a0fa0 использовать
как пассивный probe нельзя: callback 0x8410 пишет 0x1153.
Другой read-only запрос OTG 0x801c0fc4 вернул успех с ReturnedBytes=0;
его данные не декодировались и состояние OTG по нему не объявлялось.

## Установка и следующий тест

Внешняя копия полного SYSTEM до Stage и файлы текущей 1844 сохранены и сверены
до активации; SYSTEM прочитан Microsoft Offreg и python-registry.
Предпросмотр отката выбирает только новый oem138 и возврат к oem53/1844.
Фактический offline Apply не испытывался. Полный SYSTEM также откатывает
прочие системные изменения после snapshot. Ранее созданные откаты сохранены.

После ручного Restart без хаба — одно подключение хаба с зарядкой/SSD,
затем сбор версии/хеша, питания и read-only роли ДО дальнейших переключений.
Успешной первой зарядки недостаточно: затем отдельно повторяется переход,
после которого раньше питание переставало определяться.
Не проверять исчезновение питания во время записи на накопитель.

r3 не включает отдельный Type-C lockfix, не добавляет быструю зарядку и
не гарантирует непрерывную работу хаба при смене питания. Один успешный boot
или тест сборки не гарантирует отсутствие BSOD.

## Результат аппаратного этапа

Первая загрузка прошла, начальная зарядка/USB работали. Возврат зарядки после одного отключения от хаба — FAIL, роль осталась SOURCE. [Наблюдения и r4 для диагностики](PMIC-R4-DIAGNOSTICS.md).
