# PMIC r2 / 1844: выбранный порт и этап аппаратной проверки

26 октября 2026 установлена r2 как **oem53.inf / 1.0.1844.0**.
Первая загрузка Windows после установки наблюдалась в 20:20:35 +05:00.
Ожидаемые oem53/1844, хеш SYS и служба RUNNING подтверждены после нового kernel boot.
**Функциональный результат — FAIL:** после серии переключений зарядка не определяется
ни напрямую, ни через хаб, накопитель при этом доступен. Это не доказательство
причины отказа и не доказанная регрессия относительно r1 при одинаковых условиях.
Тип-C lockfix остаётся неподписанным и неустановленным; battery miniclass 1680
не менялся. Задача непрерывной работы хаба и быстрой зарядки не решена.

## Изменение относительно r1

Backend nabu передаёт логический индекс 1. В r1 проверялся контекст слота 0,
из-за чего исправный слот 1 мог быть отклонён, а отсутствие слота 1 не проверялось.
r2 сначала ограничивает индекс профилем nabu [0,1], затем проверяет выбранный
контекст с шагом 0x30. Неизвестные индексы возвращают 0x61 до чтения таблицы.
Эвристика китайского fix20 по 0x1509 не переносилась на индекс 1.
Не измерено, присутствовал ли смешанный readiness в момент реального отказа.
Это исправление воспроизведённого дефекта, не доказанная причина пропадания USB.

## Проверки окончательного артефакта

- Подписанный SYS: 2072 ARM64-сценария, смешанная готовность портов,
  границы индексов, ошибки SPMI, регистры/стек и дополнительные базы загрузки.
- Windows ARM64 RtlVirtualUnwind: 130 контекстов, 0 ошибок.
- Ghidra: финальный hook и guard независимо просмотрены.
- Сборщик COFF сохраняет все семь пар .pdata/.xdata MSVC.
  Первоначальный неполный r2 дал ошибки native unwind и был отклонён
  до подписи/установки. Исправленный сборщик воспроизвёл старый r1 побайтно.
- Каталог/SYS проверены тестовой подписью; production/WHQL подписи нет.

Исходники r2 отделены от r1: [experiments/pmic-r2](../experiments/pmic-r2).
Builder принимает точные исходные бинарники по хешам и объект ARM64;
нужны pefile, а эмулятору также Unicorn и Capstone. Старые файлы src/role_repair.c
и evidence/emulation.json описывают r1 и намеренно не заменены результатами r2.

## Откат и следующий тест

До Stage сохранены полный SYSTEM, BCD и три файла текущей 1843;
внешние копии сверены по хешам до активации. SYSTEM прочитан Microsoft Offreg
и независимым python-registry, включая текущую привязку oem50.
Restore helper теперь допускает точный хеш r1; шесть тестов выбора snapshot
и guard прошли, предпросмотр реальных внешних записей проверен.
Фактический offline Apply не выполнялся. Полный SYSTEM отменяет также прочие
изменения системных настроек после снимка. Снимки/идентификаторы устройства/ключи
не публикуются.

Владелец выполнил загрузку без хаба и несколько переключений до запуска нового лога.
Его последовательность сохранена отдельно от инструментального наблюдения.
Трёхминутный read-only лог после сообщения: AC offline, Charging=0, Discharging=1,
хаб и накопитель доступны во всех отсчётах. Нового BSOD в выбранных системных
событиях не найдено; есть отдельные WUDFRd 219 на других ACPI-узлах, причина
текущего отказа ими не установлена. Дальше — ограниченная ETW-трасса USB/UCM
на внутреннем диске и контролируемое повторение перехода без записи на SSD.
Трасса не равна измерению VBUS или PMIC-регистров.
До проверки питания не испытывать отключение зарядки во время записи на SSD.
Проверки сборки не гарантируют отсутствия BSOD.
