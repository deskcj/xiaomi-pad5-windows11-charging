# Восстановление питания, второй charger и сохранение USB-сессии

27.10.2026. Продолжение статического расследования. Нет новой сборки,
установки, эмуляции, физических тестов, перезагрузки или опроса оборудования.
Анализируются сохранённые SYS/ELF, исходники nabu и архивный SYSTEM.

**Готового подтверждённого исправления пока нет.** Подготовлен отдельный

## 1. Generic ParallelCharging по умолчанию выключен

В qcbattmngr10730 (SHA3659A20DE0606AA7283EA3197A1C212E28BFEC212C838914F19D74BE629453A3)
функция16CB0 инициализирует конфигурацию по указателю286B0:

```text
16DFC: STRB WZR,[config,#208]   // feature flag = 0
16E00: STR  WZR,[config,#20C]   // input power distribution config = 0
```

1F510 строит путь через WdfDriverGetRegistryPath и добавляет
`\ParallelCharging`. Параметр FeatureEnable с допустимым значением0/1
меняет первый байт этой части конфигурации. WDF-индексы подтверждены
локальным WDK:117 — GetRegistryPath,229 — RegistryOpenKey.
DriverGetRegistryPath возвращает путь в Services.
[Microsoft WDF](https://learn.microsoft.com/en-us/windows-hardware/drivers/ddi/wdfdriver/nf-wdfdriver-wdfdrivergetregistrypath).

В сохранённом SYSTEM (SHA5550A5835BCE7D6B2D7D757F3C55A910B902F04CF782693DCEDCF1A1B18727B2)
для Services\qcbattmngr отсутствуют Platform, ParallelCharging и
ParallelCharging\ThermalBalancing. Файл прочитан python-registry без
монтирования; SHA до и после одинаков. Это историческая конфигурация,
а не новое чтение текущего реестра.

Следствие ограничено: **показанный механизм настройки не включает generic
parallel-путь в этом архиве**. Это не доказательство отсутствия любого
другого драйвера помпы или невозможности её поддержки в Windows.
Начальные нули BSS в самом PE также не являются измеренными значениями
на работающем устройстве — важна именно найденная инициализация16CB0.

В1AFE8 флаг+208 разрешает работу второго charger, а+20C выбирает вариант
распределения. Разобраны20230/206B0/20A20/20DF0: там отдельные состояния,
распределение входной мощности/тока и запросы ко второму target, включая
семейство IOCTL8029. Часть пути затем вызывает общую213A8 основного charger.
Следовательно, наличие generic-функций ещё не означает готовую совместимость
этого интерфейса с LN8000.

**Не предлагается создать FeatureEnable=1.** Сначала должны быть установлены
драйвер второго target, совпадение ABI, модель чипа, питание и ограничения.

## 2. Android управляет помпой отдельно и тоже требует проверки ошибок

В DTS nabu есть узлы BQ2597x по адресу66h и LN8000 по51h. Наличие обоих узлов
в исходнике не доказывает наличие обоих чипов на конкретном планшете.
[DTS nabu](https://github.com/MiCode/Xiaomi_Kernel_OpenSource/blob/71b6effd2dfa8f703dd1ea17acd1323b2fd3cf6c/arch/arm64/boot/dts/qcom/nabu-sm8150.dtsi#L165).

Добавлены разборы архивного Android ELF:

| VA | Функция | Подтверждённое поведение |
|---|---|---|
|FFFFFF8008CD1BD8|ln8000_charger_set_property|Разные ветви Present, ChargingEnabled, лимита входного тока, напряжения и защит QC3 |
|FFFFFF8008CD26E8|ln8000_update_opmode|Чтение SYS_STS и различение standby/bypass/switching |

Путь включения помпы меняет режим, ждёт10мс, перечитывает режим и затем
сохраняет chg_en. В исходнике psy_chg_set_charging_enable результат
ln8000_change_opmode не проверяется; функция возвращает0 и сохраняет
запрошенный enable. В update_opmode результат чтения SYS_STS также не
проверяется: в бинарнике после BL поCD2710 сразу идёт LDR/TST поCD2714/18,
без ветви проверкиW0.
[Точный LN8000-исходник](https://github.com/MiCode/Xiaomi_Kernel_OpenSource/blob/71b6effd2dfa8f703dd1ea17acd1323b2fd3cf6c/drivers/power/supply/ti/ln8000_charger.c#L958).

Это не утверждение о реально произошедшем I²C-сбое. Но такой путь нельзя
переносить как гарантию: requestedEnable, подтверждённый opmode и валидные
измерения должны различаться. Ответ API «успех» и записанный chg_en сами
по себе не доказывают фактическую зарядку. Непроверенный ADC не превращается
в физическое отключение кабеля.

## 3. Battery-события существуют: отсутствие всех уведомлений не подтверждено

Прослежены конкретные цепочки qcbattmngr:

```text
ChargerInhibit, таблица28560 -> E590 -> A1C8(event B)
    -> event29380 -> worker9490 case B -> B200

UsbUv, таблица28600 -> E6F0 -> A1C8(event D)
    -> event29780 -> worker9490 case D
```

9490 ждёт17 событий; B200 выбирает обработчик по внутреннему состоянию+A88
из таблицы283E8. Для состояний1..9 используется общий BF50; он проверяет
новое состояние и вызывает зарегистрированный callback через28A48.
Регистрация разрешена доCE48: при context+9C0=1 указатель28A48 получает149C0,
а соседний28A40 —146A0. При другом значении используются DB10 иDAC0.
Сам выбор приходит из первого элемента ACPI-пакета BMNR через4148;
загрузчик4D08 также допускает override Services\qcbattmngr\WDF\SelectPlatform.
В архивном SYSTEM ключ WDF в корне этой службы отсутствует. Значение
фактически полученного BMNR в имеющихся материалах пока не установлено.
Поэтому выполнение конкретной платформенной ветви в прошлых сбоях
не подтверждено. Это уточнение относится и к ранее разобранным
146A0→17EE8/213A8: дефекты ветвей установлены статически, их активность
на планшете требует отдельного подтверждения без угадывания по названию.
Проверены также AF78 и8FE8: это обработка сохранённых данных/уведомлений,
а не найденная независимая команда снятия USBIN suspend.

Таким образом, нельзя объяснять весь сбой словами «battery manager вообще
не получает событий». Событийная инфраструктура есть. В этих обработчиках
не найдено прямого сброса сохранённых USB/DC-флагов29121/2911A иvalid2911B.
Ранее найденная несогласованность кэша остаётся возможным сценарием, но
**не доказано**, что любое событие обязательно оставит порт без восстановления:
изменение внутреннего состояния может вызвать другой запрос.
Это другой канал событий; находка не отменяет прежний пробел формирования
виртуального Type-C Fault-alert в FAD8.

Ход конкретного прошлого отказа без временной трассы не восстановлен.
Новых измерений для этого не делалось. Следующий полезный статический
шаг — найти архивное BMNR/профиль прошивки и завершить условия переходов
для выбранного алгоритма. Периодический reset USB не решает этот вопрос.

## 4. Восстановление через Stop не является непрерывной работой SSD

Документация Windows прямо определяет: UcmTcpciPortControllerStop заканчивает
PD-контракт и Type-C-соединение. Поэтому использовать Stop/Start как обычную
реакцию на вынимание блока питания из исправного хаба нельзя считать
выполнением требования «копирование продолжается без обрыва».
[Microsoft Stop](https://learn.microsoft.com/en-us/windows-hardware/drivers/ddi/ucmtcpciportcontroller/nf-ucmtcpciportcontroller-ucmtcpciportcontrollerstop).

При подтверждённой ошибке, требующей остановки контроллера, корректное
завершение и восстановление остаются необходимыми. Это отдельный сценарий
восстановления после обрыва. Аналогично USB port reset/cycle требуют учёта
передач и перечисления устройства.
[Microsoft USB recovery](https://learn.microsoft.com/en-us/windows-hardware/drivers/usbcon/how-to-recover-from-usb-pipe-errors).

Нарушение этих правил в конкретном callsite установленного драйвера здесь
не заявляется. Это проверенные ограничения проектируемого решения.

## Результат этапа

Составлен контракт с отдельными состояниями HubSinkHost/HubSourceHost,
поколениями подключения и операций питания, обработкой Unknown и
согласованным владельцем suspend/ICL. В нём есть переходы загрузки с хабом,
снятия/возврата зарядки, прямого SSD, прямой зарядки и смешанных последовательностей.

Чек-лист остаётся32 сценария/14 условий. Уточнены быстрый режим помпы,
ошибки измерений и запрет считать Stop/reset непрерывным I/O. Пункты
не отмечаются пройденными. Новые настройки в Windows не применялись.
