# r2: USB-переподключения записаны, зарядка не вернулась

После сообщения владельца сохранена завершённая десятиминутная ETL:
8372 события, EventsLost=0, около 1.5 MB. Сам ETL с идентификаторами и указателями
остаётся в локальном проекте. Публично публикуется обезличенный отчёт.

592 нативных отсчёта с 20:34:25 до 20:44:25 (+05:00): AC offline,
Charging=0, Discharging=1. Показанный процент уменьшился 98→97.
Записаны две последовательности исчезновения и возврата хаба/SSD:

| Native CM observation | Hub | Storage |
|---|---|---|
| 20:43:04.621 | отсутствует | отсутствует |
| 20:43:31.157 | доступен | отсутствует |
| 20:43:32.196 | доступен | доступен |
| 20:43:58.756 | отсутствует | отсутствует |
| 20:44:08.944 | доступен | отсутствует |
| 20:44:10.949 | доступен | доступен |

Это время программного опроса, не время физического изменения VBUS.
Владелец описал несколько перестановок вместо одного запрошенного перехода:
после безопасного извлечения подключал зарядку напрямую (без результата),
затем хаб с зарядкой без накопителя (без зарядки), в конце вернул хаб с обоими.
Однозначное сопоставление каждого действия конкретному событию не установлено.

## Что трасса позволяет утверждать

USB-стек получает события отключения и снова перечисляет устройства.
Зарядка во всём нативном интервале не вернулась. Непрерывность записи на SSD
не испытывалась, никакие копирования во время переключений не запускались.
Измерения напряжения/тока на USB и PMIC-регистров нет.

Локальные описания событий Microsoft USBHUB3 расшифрованы: 179 — Client Initiated
Recovery Action, 123 — Failure during Port Change Request, 130 — Hub Control
Transfer Error, 173 — SuperSpeed Device is Connected on the 2.0 Bus.
В 179 встречается URB 0x1E: WDK определяет его как SYNC_RESET_PIPE_AND_CLEAR_STALL.
Код 0xC000000E определён как STATUS_NO_SUCH_DEVICE. Эти события, особенно
на фоне физических отключений владельца, не доказывают причину отказа зарядки.

## Ограничение записи USB-C

UcmCx и UcmTcpciCx были включены в конфигурацию сбора, но событий этих
провайдеров в сохранённом ETL нет. Их GUID присутствуют в текущих системных SYS,
сервисы UcmCx0101 и UcmTcpciCx0101 RUNNING. Отсутствие событий само по себе
не доказывает, что менеджер не работает или что найдена причина сбоя.

По read-only совпадению GUID зарегистрированных провайдеров с точными бинарниками
найдены дополнительные Qualcomm-провайдеры:
- qcusbctcpm8150.sys: 246e500b-1764-4427-add6-3c998b71f899, RVA 0xB288;
- qcpmictcc8150.sys: 9cab7ef0-9c6f-4c3a-a5ac-ff2e59e181ec, RVA 0x182F8.

В первой трассе они не были включены. Подготовлена конфигурация следующего
сбора с этими провайдерами; наличие событий/их полная расшифровка ещё не проверены.
Автоматическая проверка отклонила дополнительный короткий повышенный запуск:
blocked by policy, без подробной причины. Он не выполнялся, обход не предпринимался.

tracerpt предупредил о частичном несовпадении схем и отобразил смещение +04:59.
Для таблицы использованы только нативные timestamps +05:00; из разных часов
не вычислялись миллисекундные задержки. Исходные ETL/XML сохранены для проверки.

Состояние: r2/1844, первая загрузка прошла, зарядка FAIL, причина не доказана.
Новых kernel-драйверов, записей PMIC, сбросов контроллеров или изменений BCD
на этом этапе агент не выполнял. Type-C lockfix пока не установлен.
