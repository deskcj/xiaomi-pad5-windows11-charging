# 1853: отдельная защита аппаратных регистров TCPM

28.10.2026. Собран и тестово подписан клиент qcusbctcpm8150,
INF1.0.1853.0. Пакет остаётся офлайн. На планшете1851; соседние драйверы,
резервы, BCD и сертификаты не менялись. Полная работа зарядки/USB ещё
не подтверждена. В package находятся только SYS/INF/CAT клиента.

## Конкретная исправленная ошибка

В предыдущем разборе Ghidra установлено: приватный PEP-интерфейс вызывает
TCPM2E50, а Reference/Dereference44D0/45B0 меняют только байт C590.
ReleaseHardwareE9E0 вызывает2D08, который освобождает четыре MMIO mappings
даже при ненулевом C590. После этого прежний callback способен прочитать
NULL mapping+12000 на3240. Контрпример был задан стендом; такой порядок
Windows PnP в реальном ядре пока не наблюдался.

Теперь2BD0 и2D08 переходят в новые Map/Unmap. Перед освобождением закрывается
допуск provider и ожидаются уже принятые вызовы. Новая функция приватного
интерфейса проверяет этот допуск прежде, чем обращаться к пакету/регистрам;
после release возвращает STATUS_DEVICE_NOT_READY. Reference-byte больше
не используется как доказательство безопасности MMIO. Эта защита отдельна
от Start/Stop класса: PEP может обращаться до D0Entry, но после успешного
PrepareHardware.

Map публикует готовность для provider только после получения всех четырёх
отображений. Их физические адреса, размеры и атрибут0x204 сохранены из
оригинала. Частичная ошибка освобождает уже полученные mappings. Unmap не
вызывается с NULL и не освобождает один mapping повторно. Блокировка
жизненного цикла не удерживается при выполнении самого provider.

Оригинальный PrepareHardware ошибочно мог вернуть0 после ошибки mapping.
Новый callback проверяет результат и необходимые mappings, возвращает
ошибку ресурсов при неполной подготовке. KMDF вызывает ReleaseHardware и
после неуспешного PrepareHardware; этот путь тоже проверен. Источник:
https://learn.microsoft.com/en-us/windows-hardware/drivers/ddi/wdfdevice/nc-wdfdevice-evt_wdf_device_prepare_hardware

## Встраивание и сохранённые исправления

- Сохранены клиентские transport/timeout/cleanup исправления1851 и
  alert/D0/Start/Stop защита1852.
- Оригинальные тела PrepareE7A0, ReleaseE9E0 и provider2E50 сохранены.
  Новое Prepare вызывается из штатной WDF-регистрации E14C/E150.
- Штатный конструктор private INTERFACE41F0 публикует новый provider
  через исправленную пару438C/4390. Его исполнение проверено на машинном коде.
- Старые записи CFG сохранены, добавлены четыре новых entry points;
  проверены адреса после ASLR. Старые imports/IAT/base relocations сохранены.
- .skcode имеет RX, .skmeta R, .skdata RW. Секций RWX нет. Entry-point
  исходного драйвера сохранён; все изменения исходных секций перечислены.

57 provider-сценариев выполняют настоящий новый PE, штатные Prepare/Release,
регистрацию интерфейса41F0 и исходный provider2E50. Внешние WDF/NT вызовы,
MMIO и один не-MMIO cleanup-helper27A0 моделируются. Проверены три базовых
адреса, SP, сохраняемые регистры и X18. Отдельно исполнен фрагмент построения
адресов WDF callbacks; это не полное выполнение DeviceAdd в ядре.

При удерживаемой ссылке интерфейса1 поздний вызов после настоящего release
теперь возвращает DEVICE_NOT_READY без входа в исходный provider. Проверены
частичные отказы5 этапов отображения, cleanup/release и успешный retry.
Постоянный владелец не освобождается принудительно: ограничен только бюджет
эмулятора, а production-код продолжает пассивное ожидание.

Совместный тест связывает новый1853 PE со скомпилированным лабораторным
PEP-модулем из1852. Используются настоящий исходный PEP callback, реальный
новый INTERFACE constructor и функции Reference/Dereference.256 циклов:
256 heap allocations/frees,256 references/dereferences,2048 mappings/unmaps,
всего768 принятых provider-вызовов. Вызовы между unmap и повторным map
блокируются; остаточных mappings/буферов нет в этой модели.

Это не256 реальных переподключений. MMIO — инертная RAM; электрический PD,
физический SMP, реальное ядро/WDF и USB topology не проверялись. PEP-модуль
в этом тесте — COFF, без собственного полного SYS/CFG/native-unwind QA.

Native unwind выполнен средствами Windows ARM64 с SYS как неисполняемыми
данными. Включены перенаправленные начала2BD0/2D08 и исходные вложенные
Prepare/Release/provider кадры. Компилятор оставляет перед стековым кадром
нового provider короткий stackless prefix. Он отдельно доказан как leaf
без изменения SP/NV/LR и проверен native unwind; отсутствие runtime-record
ровно на первом байте здесь не заменялось фиктивной записью.

## До аппаратной активации

1. Закончить полный PEP2141 PE: лабораторный модуль ещё не встроен/подписан.
   В установленном PEP2140 остаётся heap lifetime дефект0x13A; клиент1853
   не исправляет запись PEP в его собственный освобождённый буфер.
2. Проверить PEP IRQL, unregister/shutdown и lifetime образа/interface при
   выгрузке. MMIO rundown действует, пока код provider остаётся загруженным.
3. Закрыть initial pending-alert replay и подтвердить одного producer
   ClassAlert. Этот вопрос наследуется от1852.
   Отдельно доказать доставку первого PEP power request после готовности
   MMIO: пока MappingState закрыт, callback возвращает DEVICE_NOT_READY.
   Лабораторный PEP сейчас игнорирует этот status и не ставит автоматический
   retry. Безопасное отклонение не доказывает корректный cold boot; в joint
   retry-тесте второй power-вызов задан стендом явно, а не создан драйвером.
4. Затем проверять ложный AC, направление питания/роль данных, первый
   запуск с хабом и непрерывность SSD. Эти функции пока не приняты.

Функциональный чек-лист лежит рядом. Исходные1852 и существующие резервы
сохранены. Никаких установок, сбросов USB, кабельных циклов и перезагрузок
в этой сессии не выполнялось. Девять установленных payloads сверены по SHA256.
