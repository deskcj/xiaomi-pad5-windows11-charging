# Следующее исправление PEP: скомпилированный лабораторный модуль

pep_lifetime.c собран EWDK ARM64 с /kernel /W4 /WX /GS /guard:cf и прошёл
статический /analyze без предупреждений. Это COFF-объект, НЕ готовый SYS,
без установочного INF/CAT. На планшет не устанавливался. Число2141 здесь
обозначает направление следующего эксперимента, а не установленную версию.

## Что делает модуль

- Закрывает приём power-вызовов перед освобождением интерфейса/буфера,
  ждёт принятые вызовы и обнуляет опубликованные указатели.
- Освобождает каждый успешно полученный интерфейс через Dereference;
  повторные arrival/removal обрабатывает без повторного free или query.
- Очищает состояние после create/open/query/allocate failure, возвращает
  ошибку при отказе выделения и допускает следующую попытку подключения.
- Передаёт провайдеру отдельный24-byte пакет на стеке каждого вызова.
  Имя URS0/URS1 подготавливается и на первом flag1, и после смены порта.
  Общий heap-пакет исходного PEP не используется для power-уведомлений.
- Сохраняет порядок provider-before-platform для включения и
  platform-before-provider для выключения. Ссылка rundown не удерживается
  через platform-вызов, способный вызвать PnP-обработку. Не-TypeC путь
  делегируется исходной функции вместо отключения всего PEP.

## Что реально исполнено

test_lab.py связывает машинный код НОВОГО COFF с НАСТОЯЩИМ PEP2140 и
НАСТОЯЩИМ TCPM-провайдером2E50/44D0/45B0. Внешние WDF/NT/allocator/platform
DDI, ABI security-cookie helpers и задержки заменены моделями. USB MMIO
отображён как инертная RAM. Это проверка lifetime/формата/ошибок, не модель
электрических регистров и не проверка работающего USB/PD.

Пройдено16 сценариев, в том числе1/2/10/100/256 циклов. Для256 циклов:
256 выделений,256 освобождений,256 InterfaceReference и256 Dereference,
оставшихся буферов0. Отказ выделения и Query больше не оставляет состояние,
которое блокирует повтор. Первый flag1 перед любым flag0 доходит до реального
провайдера с корректным именем вместо прежнего NULL. Проверен порядок
ожидания перед free и отсутствие lease через platform callback.

Никакого SYS-образа для PEP тест не создаёт. Original callback380D0 вызывается
непосредственно из лабораторного COFF. Подключение в таблицу PnP и все
power-call sites настоящего PE пока не выполнены. Не проверены native unwind
этого модуля, реальные уровни IRQL, физический SMP, unregister/unload и
внешний ReleaseHardware провайдера. IRQL и аппаратное lifetime нельзя
считать исправленными только по успешной эмуляции.

## Обнаруженный дефект COFF-загрузчика

При испытании поля Interface.Notify+32 выявлен неверный пересчёт addend
IMAGE_REL_ARM64_PAGEBASE_REL21: в COFF он хранится в байтах, а не страницах.
Исправлено в лабораторном загрузчике и tools/link_backend.py. Независимый
пример с полем через границу4KiB слинкован настоящим Microsoft LINK:
весь текст исправленного алгоритма совпадает, прежний алгоритм отличается.
DLL-пример никогда не загружался/исполнялся; он только источник байтов.

Для точных1851 backend/client и1852 client отдельно сверены SHA256 объектов
с build manifests: все145/8/52 ADRP-addends равны0. Поэтому данный дефект
НЕ меняет эти три сборки и НЕ объясняет текущий аппаратный сбой.1852 ещё
раз собрана исправленным алгоритмом в новой папке: итоговый SYS идентичен.

Первичный источник по обработке COFF addend:
https://llvm.org/docs/doxygen/RuntimeDyldCOFFAArch64_8h_source.html

## Как продолжать

Повторный Ghidra-разбор с полными границами функций по .pdata установил:
WDF PrepareHardware=E7A0, ReleaseHardware=E9E0; mapper2BD0 публикует C538,
C528,C530,C520, а unmapper2D08 освобождает их независимо от reference-byte
C590. Ненулевой C590 вызывает лишь диагностическую запись. Повторный поиск
ссылок через базу Ghidra не вернул refs к этим globals; это ограничение
имеющегося проекта, а не доказательство отсутствия обращений. Полные
дизассемблер/декомпиляция сохранены в build/provider-lifetime-complete.txt.

В дополнительном отрицательном тесте исполнен настоящий2D08 при имеющейся
ссылке интерфейса1: четыре mappings обнулены; следующий настоящий2E50
падает на3240 (NULL mapping+12000). Это заданный стендом порядок между
модулями; наличие такого порядка в реальном Windows PnP пока НЕ доказано.
Он подтверждает, почему одного PEP-rundown недостаточно: нужен отдельный
provider-gate между успешным PrepareHardware и началом ReleaseHardware.
В lab-results.json он записан как оставшийся небезопасный контрпример,
а не как ещё одна исправленная функция или пройденная аппаратная проверка.

1. Разобрать время жизни MMIO TCPM относительно ReleaseHardware: собственный
   PEP-rundown не удерживает чужие mappings от независимого освобождения.
2. Закончить совместную защиту provider/consumer, unregister и shutdown.
3. Встроить объект в полный PEP PE через проверенные call sites без слепых
   prologue trampolines; включить CFG/relocations/native unwind/rebuild QA.
4. Проверить начальные pending alerts нового TCPM и их единственного producer.
5. Только затем переходить к реальной зарядке/ролевым переходам и SSD.

Файлы build/lab-results.json, build/identity.json,
build/relocation-oracle.json и build/existing-object-addends.json фиксируют
разные виды доказательств. Ничего из этого не равно готовности к установке.
