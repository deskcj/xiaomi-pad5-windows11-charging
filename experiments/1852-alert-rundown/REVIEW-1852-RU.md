# 1852: защита уведомлений TCPM, 28.10.2026

Собран и подписан отдельный клиент qcusbctcpm8150 версии INF 1.0.1852.0.
Установленная связка1851 не изменялась. Это проверенный офлайн кандидат
для устранения одного класса падений; полноценное исправление питания
и безопасная установка всей связки ещё не доказаны.

## Что исправляет код

Второй дамп102726-10640-01.dmp показывает0x7E/C0000005 на client+8ABC:
оригинальный обработчик разыменовывал NULL-контекст по адресу0x80.
Новый обработчик89E0 проверяет входные параметры, ожидаемый WDFDEVICE,
результат typed-context lookup и текущий контроллер. Он допускает вызовы
класса только после успешного Start и закрывает допуск перед D0Exit/Stop.
Остановка ждёт уже принятые уведомления; принудительного освобождения
чужой операции по таймауту нет. Старый queued Start после начала D0Exit
не должен повторно открыть допуск. Блокировка жизненного цикла не удерживается
во время ClassAlert: класс может синхронно вызвать обработчики ввода-вывода.

Оригинальные D0Entry1C10 и D0Exit1E50 сохранены. В WDF-регистрации заменены
адреса callbacks; оригинальные записи CFG сохранены и добавлены два новых
адреса, включая проверку их перемещения при ASLR. Native ARM64 unwind
сгенерирован компилятором; короткие адаптеры Start/Stop отдельно проверены.
Все клиентские исправления1851 для transport/timeout/cleanup сохранены.
Backend, PMIC, батарея, PEP, URS/xHCI и камера этим пакетом не заменяются.

## Что остаётся до установки

1. Установленный PEP2140 содержит отдельный дефект lifetime, связанный
   с0x13A/qpeY: удалённый24-byte буфер остаётся опубликованным. Исправление
   клиента1852 не исправляет PEP. Также нужны баланс InterfaceDereference,
   очистка после ошибки Query/Allocate и подготовка имени до первого flag1.
2. Проверить начальные уведомления во время ClassStart. Новый безопасный
   допуск закрыт до успешного возврата Start: нужен аудит/повторное чтение
   pending-статуса, чтобы не потерять первое событие подключения.
3. Подтвердить единственного последовательного производителя ClassAlert.
   Счётчик rundown защищает время жизни, но не является очередью уведомлений.
4. Ложный значок AC после отключения, разделение собственной OTG-подачи и
   внешнего питания, непрерывность SSD и электрические переходы PD здесь
   не исправлены и не проверены. Отсутствие BSOD не равнозначно зарядке.

## Повторный Android/Ghidra разбор

Открыт AndroidPD27 в Ghidra -readOnly -noanalysis. В оригинальном ядре
smblib_notify_usb_host по адресу FFFFFF8008CAE2E0 пишет OTG_EN в1140,
а затем сообщает EXTCON_USB_HOST. smblib_set_prop_typec_power_role по
FFFFFF8008C9F790 отдельно меняет роль питания через1544. Это подтверждает
необходимость раздельно учитывать роль данных и направление питания;
этим двум функциям нельзя приписать готовый Windows PD handover.

Повторно прочитан MiCode smb5-lib-nabu.c: обычный USB_ONLINE определяется
POWER_PATH_STATUS/USE_USBIN/VALID_INPUT_POWER_SOURCE, а не одним OTG_EN.
В Android есть отдельные исключения голосования JEITA/termination/pump.
Декомпиляция сохранена в build/android-role-recheck.txt. Часть статических
символов отсутствует в таблице ELF; отсутствие имени в отчёте не означает
отсутствие функции. Предыдущее побайтное сопоставление ONLINE/PRESENT с
сырьём ELF сохранено в investigation-2026-10-28.

## Продолжение PEP в этой же сессии

next-pep/pep_lifetime.c собран в native ARM64 COFF и прошёл /analyze.
Новый машинный код связан в эмуляторе с настоящими PEP2140 и TCPM-провайдером.
16 положительных сценариев включают256 циклов с равным числом выделений,
освобождений, Reference и Dereference. Есть очистка/повтор при ошибках и
корректный первый flag1; общий освобождаемый heap-пакет заменён пакетом на
стеке каждого вызова. PEP SYS/INF/CAT для этого модуля ещё НЕ создавались.

Затем найден конкретный оставшийся межмодульный риск: Ghidra с границами
по .pdata показывает PrepareHardwareE7A0 → mapper2BD0 и
ReleaseHardwareE9E0 → unmapper2D08. C590 — счётчик ссылок интерфейса —
в2D08 используется только для диагностики, а не для удержания mappings.
В отрицательном тесте настоящий2D08 обнуляет четыре отображения при
reference=1, и последующий настоящий2E50 падает на3240. Это искусственно
заданный порядок событий; его возникновение в реальном PnP пока не доказано.
Следующая правка должна закрывать provider перед ReleaseHardware и ждать
его активные вызовы. Успех16 PEP-сценариев не объявлен полной безопасностью.

При подготовке модуля также найден и исправлен addend-дефект COFF-загрузчика.
Пример с переходом поля через границу4KiB побайтно сверён с Microsoft LINK.
Все ADRP-addends точных объектов1851 backend/client и1852 client равны0;
этот дефект не затрагивает их байты.1852 повторно собрана исправленным
алгоритмом: итоговый SYS побайтно тот же. Подробности и первичный источник
LLVM приведены в next-pep/README-RU.md.

Подробный функциональный план — FUNCTION-CHECKLIST-RU.md. Установок,
перезагрузок, USB reset и новых ручных переключений кабелей в этой сессии нет.
